# 파일 덮어쓰기 실패 보존 검증

기록일: 2026-10-19. 검증 당시 커밋 미기록(로컬 변경 상태). 커밋·푸시·운영 배포 없음.

후속 2026-10-21: [실제 개발 앱→로컬 DB 검증](OVERWRITE_LOCAL_DB_VERIFICATION.md)에서 복사·이동 승인 준비 잠금 실패, 승인 후 실행 재검증 잠금 실패, 새 요청 성공을 확인했다. 아래 10-19의 미실행 표기는 당시 범위로 보존한다. 실제 장치 I/O·커밋 실패, 다른 파일 시스템 등 미검증은 그대로 유지한다.

## 기존 사용자 수동 통과 유지

- 복사·이동 덮어쓰기 성공, 충돌 취소, 다른 이름 저장·확장자 자동 추가, 승인 이후 대상 변경 차단은 기존 사용자 수동 통과 그대로 유지함. 이번 자동 시험으로 해당 수동 기록을 대체하지 않음.
- 실제 UI에서 캡처 미리보기를 1시간 이상 유지하는 시험은 사용자 요청에 따라 대기 유지.

## 구현·지원 범위

- 공통 `file_operations::execute`가 충돌 등록 → 일회성 승인 → 동일 작업/인자/대상 및 지문 확인 → Windows TxF 트랜잭션 교체를 수행함.
- 동일 볼륨의 지원되는 일반 파일, 단일 하드링크, 512 MiB 이하, reparse point·추가 데이터 스트림이 없는 조건으로 제한됨. TxF가 불가능하면 비트랜잭션 교체로 전환하지 않음.
- 기존 대상을 먼저 삭제하지 않음. 이동 원본 삭제는 트랜잭션 안에 예약하고 커밋 실패/중단 시 롤백함. 트랜잭션 핸들과 파일 핸들은 Drop으로 해제됨. 덮어쓰기 경로는 별도의 `.tmp` 파일을 만들지 않음.
- 제품 보존 결함은 이번 범위에서 발견되지 않음. 기존 실패 테스트가 지원 불가 거부도 롤백 성공처럼 통과시킬 수 있었던 검증 공백을 보완함. 실패 지점 도달을 반드시 검사하고 정확한 오류를 요구함.
- 실패 주입은 `cfg(test)` thread-local 상태만 사용함. IPC·환경변수·일반 개발 앱·배포 빌드에서 활성화할 수 없음. 기존 커밋 직전 중단 인자도 `cfg(test)`로 제한함. 운영 정책·승인 검증은 유지함.

## CLI 실제 Windows 파일 시스템 결과

`cargo test --manifest-path ace-desktop/src-tauri/Cargo.toml file_operations::tests -- --nocapture` 실행: 당시 9개 통과. 이후 추가한 ADS 거부 시험 1개를 별도 실행하여 통과. 중복 합산하지 않음.

| 조건 | 실제 수행 / 결과 | 해석 |
| --- | --- | --- |
| 복사·이동 대상에 배타적 Windows 파일 핸들 유지 | 두 파일 존재·SHA-256 보존, 잠금 해제 후 새 승인 요청 성공 | 실제 OS 거부. 쓰기 전 거부이며 작업 중 복구 성공 아님 |
| 추가 스트림이 있는 원본 | 복사·이동 모두 SAFE_OVERWRITE_UNAVAILABLE, 원본·대상·스트림 SHA-256 보존, 추가 파일 없음, 승인 소비 | 실제 지원 제한 거부. 비NTFS 볼륨 자체를 시험한 것은 아님 |
| 현재 로컬 볼륨의 트랜잭션 지원 | 실제 복사·이동·이름 변경 성공 분기 확인 | 이 볼륨 조건의 결과, 범용 지원 선언 아님 |

## 실패 주입 + 실제 Windows TxF 결과

모의 파일 시스템이 아니라 실제 임시 폴더·파일·Windows 트랜잭션에 **오류 발생 시점만 합성**함. 실제 디스크 부족·장치 고장·OS 커밋 실패 재현이라고 기록하지 않음.

- 복사·이동 각각 읽기 실패 지점, 쓰기 실패 지점, 커밋 직전 중단 지점: 총 6조건 통과.
- 읽기/쓰기 지점은 트랜잭션 안에서 실제로 대상 길이를 줄이고 4바이트를 쓴 뒤 합성 오류를 반환함. OS ReadFile/WriteFile이 실제 오류를 반환한 시험은 아님.
- 이동 커밋 직전 지점은 전체 데이터 쓰기·flush/sync와 원본 삭제 예약·핸들 닫기 후 중단함. 실제 CommitTransaction API 오류는 주입하지 않음.
- 매 조건에서 원본·대상 존재와 이전 SHA-256 일치, 폴더 내 파일 수 2개, 두 파일을 share_mode(0) 읽기/쓰기로 다시 여는 데 성공함. 잔여 승인 없음·소비한 승인 재사용 거부 확인.
- 실패 주입 해제 후 새 승인으로 정상 재실행 성공 확인. 이동 재시도 성공 때만 원본 제거됨.
- 별도 기존 커밋 직전 중단 테스트의 지원 불가 허용 분기는 제거함. 지원되지 않는 실행을 롤백 성공으로 인정하지 않음.

## 모의 API·IPC / 결과 계약

- Chrome Playwright `native-safety.spec.ts -g '덮어쓰기 실패는'`: 복사·이동 2개 통과. 실제 UI 승인 이후 합성 Native 실패 응답을 전달하여 결과 API에 FAILED 제출, SUCCEEDED 없음, 충돌창 해제·다음 전송 가능 확인.
- Rust 실패 결과 계약 시험: EXECUTION_FAILED / SAFE_OVERWRITE_UNAVAILABLE → success=false, status=FAILED, 완료 데이터 없음 검증.
- 코드상 파일 실행 오류는 `?`로 전파되고 Native `fail` 결과가 기존 executionId/attemptId를 받아 감사 로그에 전달됨. 실제 실패 주입 → 앱 감사 파일 → PostgreSQL 저장까지 연결한 종단 시험은 이번에 실행하지 않음. 위 UI 시험은 DB 저장 성공의 증거가 아님.
- 비테스트 `cargo check` 통과. Release는 기존 모델·서명 준비 조건을 유지하며 이번에 빌드/배포하지 않음.

## 미검증·다음 단계

- 실제 디스크 부족, 저장장치 I/O 고장, CommitTransaction 오류/전원 단절, 비NTFS·네트워크·다른 볼륨 조건은 미검증. 개인 파일 권한 변경·디스크 채우기·볼륨 설정 변경 없음.
- 지금 사용자에게 위험한 디스크 실패 재현을 요구하지 않음. 지원 불가 볼륨 시험은 이미 준비된 버려도 되는 별도 매체가 있을 때만 진행하며 포맷하지 말 것.
- 실제 앱·DB의 OS 잠금 실패 추적은 10-21 후속 검증에서 수행 완료. 절차: 테스트 파일 생성·해시 기록 → 대상 배타 잠금 → 실패 단계와 동일 executionId/attemptId의 FAILED 확인 → 잠금 해제·해시 비교 → 새 요청·승인 성공 확인. 쓰기 전 거부로 기록하며 중간 쓰기 오류의 DB 추적까지 완료한 것은 아님. 관련 변경 없이 반복하지 않음.
