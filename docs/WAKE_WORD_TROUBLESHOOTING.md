# ACE Wake Word 미호출: 조사·시도·수정 기록

작성일: 2026-10-05

## 현재 상태

등록 5회와 마지막 테스트를 WebView 녹음에서 CPAL/WASAPI 입력으로 전환했다. 상시 대기와 장치 선택·채널 변환을 공유하고, 등록 완료에는 실제 마이크 스트림에서 2회 연속 최종 감지가 필요하다. 등록 음성의 과도한 앞뒤 무음도 정리한다.

**코드·자동 테스트 검증과 실제 사용자 발화 성공은 구분한다.** 자동 테스트와 빌드는 통과했지만, 도구 실행 환경의 물리 마이크 테스트는 WASAPI 접근 거부로 실패했다. 사용자 호출 인식률의 개선 수치는 아직 측정하지 못했다. 기존 개인 모델을 도구에서 덮어쓰지 않았으며, 수정본에서 재등록해야 새 입력 경로로 모델이 생성된다.

## 1. 현상과 이전 시도

사용자는 ACE를 여러 번 불러도 호출되지 않아 목소리를 5회 재등록했다. 등록 화면 테스트에서는 `detected=true`였지만 실제 대기에서 호출되지 않았다. 이후 ‘민감하게’로 변경해도 실패했다.

이전의 명령 녹음 종료·로그인·AI 서버 미연결과 이번 문제는 실패 단계가 다르다. 이번 로그는 `final_detections=0`으로 Orb 및 명령 STT/PDF 실행 이전에 실패했다.

앞선 조사 기록은 `ace-desktop/docs/VOICE_INVESTIGATION_2026-10-05.md`에 있다. 구형 모델과 기존 진단 녹음 사본에서 비교 기준만 바꾸어 재생한 결과는 다음과 같았다.

| 비교 기준 | ACE 녹음 감지 이벤트 | 일반 발화 | 무음 |
|---|---:|---:|---:|
| 0.52 | 1 | 0 | 0 |
| 0.48 | 4 | 0 | 0 |
| 0.46 | 4 | 0 | 0 |

이에 따라 개인 감도 0.48을 선택할 수 있게 했다. 이는 짧은 기존 자료의 감지 이벤트가 늘어난 결과이며, 새 발화의 성공률이나 장기 오탐률을 보장하지 않는다. 이번 작업에서 이 실험을 새 모델 대상으로 다시 실행한 것은 아니다.

사용자의 후속 로그에서도 민감 모드 미감지가 계속돼 임계값 완화만으로 해결되지 않았음을 확인했다. 이번에는 기준을 더 낮추지 않고 입력 경로와 등록 검증 방식을 수정했다.

## 2. 새 로그에서 확정한 사실

| 구간 | 모델 | 유효 기준 | 해당 구간 최고 reference 점수 | 후보/최종 감지 |
|---|---|---:|---:|---|
| 재등록 전 민감 | `ddcba3…` | 0.48 | 약 0.4066 | 0 / 0 |
| 재등록 후 기본 | `c9c4cf…` | 0.52 | 약 0.4925 | 0 / 0 |
| 재등록 후 민감 | `c9c4cf…` | 0.48 | 약 0.4628 | 0 / 0 |

- 마이크는 Microphone Array(AMD Audio Device), 48kHz, 4채널 F32였다.
- 스트림 생성/재생에 성공했고 발화 구간 RMS와 peak가 증가했다.
- 처리 프레임이 계속 증가하고 dropped=0, queue_depth=0~1이었다.
- 초기 Xrun 1회 이후 누적 횟수가 증가하지 않았다.
- 새 모델 생성·활성화·로딩 ID가 일치했다.
- `effective sensitivity`에 실제 0.48 적용이 찍혔다. 저장 모델의 원래 기준 0.52와 혼동하면 안 된다.
- 모든 구간에서 `candidate_matches=0`이었고 최고 reference 점수도 유효 기준보다 낮았다.

**직접 실패 원인은 호출어 비교 기준 탈락이다.** 마이크 중단, 처리 지연, 구형 모델 오로딩, 감도 미적용이라는 설명은 이번 로그와 맞지 않는다. 기본/민감 모드의 발화는 서로 다른 녹음이므로 점수 차이를 감도 설정 부작용으로 해석하지 않는다. 내부 비교 점수는 인식 확률이 아니다.

## 3. 구조 조사와 원인 판단

### 입력 경로 불일치와 검증의 빈틈

수정 전 구조:

```text
등록: WebView getUserMedia → WebAudio → 모노 I16 WAV → 개인 모델
등록 테스트: 같은 WebView 경로 → WAV → 뒤에 3초 무음 추가 → 오프라인 판정
상시 호출: CPAL/WASAPI → 4채널 F32 → 채널 평균 → 실시간 판정
```

등록 테스트 성공이 실제 CPAL 입력의 성공을 보장하지 않았다. 브라우저의 채널/장치 처리와 네이티브 입력 차이가 비교 점수를 낮췄을 가능성을 우선 원인 가설로 봤다. 다만 두 경로의 동일 발화 원본을 비교하지 못했으므로 특정 DSP/드라이버가 원인이라고 확정하지 않는다.

### 앞뒤 무음과 정규화 기준

등록 파일은 약 1.45~1.62초였고 발화 경계 정리가 없었다. 버튼 조작과 말하기 사이 무음까지 reference 특징에 포함될 여지가 있었다.

등록 전체 RMS 0.026~0.058과 모델 RMS 0.002009는 계산 방식이 다르다. 모델은 파일 내 프레임 RMS의 중앙값, 이어서 파일들 사이의 중앙값을 사용한다. 작은 모델 RMS 자체가 파일 손상이라는 뜻은 아니다. 긴 무음이 모델 특징과 음량 정규화 기준에 영향을 줄 가능성이 있어 경계를 정리했다. 정규화를 끄거나 공식을 바꾸지는 않았다.

### 아직 확정하지 않은 원인

- 채널 평균의 상쇄: raw_rms와 engine_rms가 표시 정밀도 내에서 같아 심한 상쇄 증거는 약하다. 임의로 첫 채널 선택으로 바꾸지 않았다.
- I16/F32 차이: 형식별 변환 코드가 존재한다. 형식 차이 자체를 버그로 단정하지 않았다.
- 최근 프레임 `rustpotter_rms=0`: 10초 누적 RMS와 측정 범위가 다르므로 전체 음성 미전달 증거가 아니다.
- 발화 거리/환경/음색 및 정규화 영향: 현재 모델의 새 양성·음성 자료로 추가 평가가 필요하다.

## 4. 적용한 해결 방안

### CPAL 등록 녹음

새 `ace-desktop/src-tauri/src/wake_setup_capture.rs`에서 등록 5회와 테스트를 수집한다.

- 상시 리스너와 `select_device`, `downmix_i16`, `downmix_f32`를 공유한다.
- 기본 입력 장치의 native rate/channel/format 및 기본 버퍼 크기를 사용한다.
- 기본 장치가 없으면 사용 가능한 장치가 하나일 때만 선택한다.
- 등록 중 장치 이름/rate/channel/format 조합이 바뀌면 재등록을 요구한다.
- 용량 12의 비차단 큐로 전달한다. 큐 손실·치명적인 스트림 오류는 성공으로 처리하지 않는다.
- 시작 시 Xrun은 즉시 치명 오류로 취급하지 않는다.
- 최대 10초 및 해당 샘플 수로 제한한다. 종료·취소 시 worker를 중지하고 스트림을 해제한다.

등록 UI의 WebView 마이크 수집과 PCM append IPC는 제거했다. UI는 네이티브 시작/종료를 요청한다. 명령 음성 녹음의 별도 WebView 흐름은 이번 수정 대상이 아니다.

### 앞뒤 경계 정리

10ms 단위 RMS를 계산해 `max(0.003, 최대 프레임 RMS × 0.08)` 이상인 첫/마지막 구간을 찾고, 앞뒤 120ms를 남긴다. 가운데 구간은 삭제하거나 이어 붙이지 않는다. 조용한 자음 보존을 위해 여유를 둔다.

정리한 샘플에도 길이·음량·클리핑 검사를 적용하며 무음은 거절한다. 에너지 기반 경계 정리이지, 일반 소리와 말을 완벽하게 구분하는 VAD는 아니다.

### 실제 스트림 테스트 두 번

- 후보 모델을 CPAL worker의 Rustpotter에 올린다.
- 상시 대기와 같은 `wake_kws::config`와 프레임 누적 함수를 사용한다.
- 실제 입력된 음성과 무음만 처리한다. 인위적인 3초 무음 추가를 제거했다.
- 결과는 한 번만 소비할 수 있다. 두 번 연속 최종 감지가 있어야 Rust의 완료 명령도 허용한다.
- 인식/품질/수집 실패 시 성공 횟수를 초기화한다. 모델 재생성은 이전 테스트를 무효화한다.
- UI는 시작 후 1초 대기 → ACE 한 번 → 2초 대기 → 종료를 안내한다.
- 테스트 중에는 Orb를 띄우지 않는다. 완료 후 기존 상시 리스너가 동작한다.

테스트 판정은 **경계를 정리하기 전의 실제 스트림**에서 수행된다. 정리된 테스트 WAV는 품질 확인과 선택적 진단 보관용이다.

### 추가 로그 및 유지한 설정

```text
native setup capture started: <device/config>, live_test=true/false
native setup capture finished: samples=..., detected=...
native setup KWS gates: GateDiagnostics { ... }
setup endpoints: raw_samples=..., retained_samples=..., live_test=...
native live onboarding test: detected=..., consecutive_passes=..., required=2; no synthetic silence
```

개발 빌드 테스트와 상시 리스너는 같은 `GateDiagnostics`를 사용한다. 기본적으로 음성을 영구 저장하거나 서버로 전송하지 않는다. 개발 진단 보관 선택 시 앞뒤 경계를 정리한 WAV를 보관하고 UI에도 표시한다. 중복되던 진단 샘플 보관 호출을 한 번으로 정리했다.

기본 reference 0.52, 민감 0.48, average 0.22, min_scores=2, eager=false를 유지했다. 새 등록 완료 시 기존 정책대로 기본 감도로 시작한다.

경계 테스트는 긴 무음 제거, 120ms 여유, 조용한 경계 보존, 무음/빈 입력을 검사했다. 컴포넌트 테스트는 5회 등록 후 첫 테스트 성공만으로 완료하지 않는 것, 실패 시 0/2 초기화, 두 번 연속 성공 시 완료, 품질/마이크 시작 실패 후 재시도를 확인했다. 실제 브라우저 렌더링이나 물리 마이크 E2E로 표현하지 않는다.

제외한 Rust 테스트 7개는 비공개 WAV fixture 필요 6개와 물리 마이크 1개다. 제외를 통과로 세지 않는다. 물리 마이크 테스트를 별도로 실행한 결과:

```text
Failed to initialize audio client:
액세스가 거부되었습니다. (os error -2147024891)
```

사용자 일반 터미널 앱은 앞선 로그에서 마이크 접근에 성공했다. 도구의 접근 거부를 사용자 앱의 기존 미감지 원인과 혼동하지 않는다. 권한 우회/임의 변경은 하지 않았다.

구현 중 CPAL 0.18의 StreamConfig 전달 형식 오류와 Clippy의 불필요한 clone 지적을 수정한 뒤 재검증했다. 새 코드의 자동 검사 통과와 사용자 음성 인식률 개선은 별개다.

## 6. 사용자 환경의 확인 절차

1. 기존 ACE를 종료하고 수정본으로 재실행한다. 개발 서버를 중복 시작하지 않는다.
2. 새 입력 경로로 목소리를 5회 재등록한다. 기존 WebView 모델을 그대로 쓰면 입력 통일의 효과를 확인할 수 없다.
3. 마지막 실제 호출 테스트를 두 번 통과한다. 시작 → 1초 대기 → ACE → 2초 대기 → 종료 순서다.
4. 설정을 닫은 상시 대기에서 정상 거리로 ACE를 10회 부르고 호출 횟수를 기록한다.
5. 일반 대화/무음에서도 의도하지 않은 호출을 확인한다. 짧은 무오탐 결과로 장기 오탐률을 보장하지 않는다.
6. 실패하면 새 모델 ID, 테스트/상시 KWS gate 점수, 입력 RMS를 비교한다. 현재 모델의 양성/음성 녹음으로 채널별 파형·정규화 영향을 한 변수씩 평가한다.

확인된 등록 검증의 빈틈을 고치고 유력한 입력 차이를 제거했다. 특정 DSP가 근본 원인이었다거나 사용자 발화 문제가 완전히 해결됐다는 최종 판정은 실제 환경 검증 이후에 내린다.

## 7. 후속 확인: 실제 Wake Word 호출 성공 (2026-10-06 정리)

사용자가 재등록 후 호출 성공을 확인했다. 아래 수치는 사용자가 제공한 실행 로그에서 읽은 값이며, 개발 도구에서 물리 마이크로 재현한 결과가 아니다.

| 항목 | 이전 등록 | 네이티브 입력 통일·경계 정리 후 |
|---|---|---|
| 모델 ID 앞부분 | `c9c4cf7b` | `88b9a7b9` |
| 등록 길이 | 1,450~1,621ms | 710~840ms |
| 참조 MFCC 프레임 | 141~159 | 66~81 |
| 모델 RMS | 0.002009 | 0.019708 |
| 실제 감지 | 기본/민감 모두 후보 0 | 기본 감도 0.52에서 최종 점수 0.65671545, partial_count=21 |
| 등록 검증 | 이전 방식의 녹음 재생 검사 | 실제 입력 테스트 2회 연속 성공, 최고 점수 0.6669 / 0.6430 |

최종 로그에 `detection accepted: forwarding to voice orb`, `voice orb activation: success`가 이어졌다. 등록 경로 통일과 무음 경계 정리 후 실제 호출이 가능해졌다는 근거다. 각각의 변경 효과를 분리한 실험은 아니므로 어느 하나만을 유일한 원인으로 단정하지 않는다. 이미 새 등록으로 성공한 사용자는 이번 오브 변경 때문에 다시 등록할 필요가 없다.

## 8. 오브 깜빡임·명령 오인식·닫히지 않음: 사건과 원인

1. **오브 깜빡임:** 기존 `VoiceOverlay`가 상태별 반복 scale/회전/opacity 애니메이션을 적용했다. 문구도 `상태:문구`를 key로 삼아 매번 사라졌다 나타났다. 코드에서 확인한 반복 효과를 제거했다. Windows 투명 창 합성 자체의 결함까지 입증한 것은 아니다.
2. **“포트폴리오예요” 오인식:** Wake Word 이후 녹음과 STT는 진행됐지만, 결과에 “열어줘”라는 실행 의도가 없어 엄격한 명령 분류가 거부했다. 사용자 발음만의 문제라고 단정할 수 없다. 해당 실패 원본 WAV가 남아 있지 않아 마이크 전처리·모델·발음 영향을 분리하지 못했다.
3. **완료/실패 후 계속 열림:** 음성 창과 메인 창 사이에 요청별 실제 실행 결과를 돌려주는 흐름이 없고, 실패 후 재청취·종료 정책도 없었다. 요청 전달 자체를 완료로 간주하면 실제 작업보다 먼저 닫힐 수 있다.
4. **Wake 로그의 0 프레임 반복:** 오브가 열린 동안 Wake 마이크를 멈추는 기존 정책 때문이다. 이 로그만으로 마이크 고장을 뜻하지 않는다. 오브 종료 시 active 상태를 해제하여 다시 Wake 대기로 돌아가게 한다.

## 9. 구현한 해결 방안

### 표시와 소리

- 호출할 때만 약 480ms 등장 효과를 재생한다. 상태/문구/재시도 변경으로 오브를 다시 만들지 않는다. 모션 감소 설정에서는 등장 효과를 생략한다.
- 본체와 테두리의 반복 확대·회전·점멸을 제거했다. 발화량에 따른 주변 광량 변화도 0.50~0.65로 제한하여 전체 오브를 숨기지 않는다.
- 불투명한 중심부를 키우고 주변 층의 색 비중을 13%에서 32%로 높였다. 중심부는 원래도 불투명했으므로 창 전체 투명도를 임의로 바꾼 것은 아니다.
- 문구와 최대 3개 선택지를 오브 왼쪽 위 말풍선으로 이동했다. 긴 문구/선택지는 스크롤된다. 창을 380×420으로 확장했다.
- 약 0.3초의 자체 합성 알림음을 추가했다. 설정의 **음성 호출 알림음**에서 켜고 끄며 PC에 저장한다. 켜면 미리 듣는다. 알림음 종료 후 녹음을 시작하고, 음성 재시도에서는 소리를 다시 재생하지 않는다.

### 세션 종료와 재청취

- 요청 UUID를 붙여 메인 창 실행 결과를 음성 창에 전달한다. 실제 SUCCESS를 받은 시점부터 **3초 후 닫기**를 시작한다.
- 인식 불일치/실행 실패 시 메시지를 표시하고 **5초 동안 재청취**한다. 말이 없으면 닫고, 5초 직전에 말하기 시작해도 발화를 계속 받는다. 다시 실패하면 같은 흐름을 반복한다.
- 발화 후 **1.5초 무음**으로 녹음을 마친다. 기존 **녹음당 30초 상한**은 유지한다. 현재 발화 판정은 RMS 에너지 기반이므로 사람 목소리와 주변 소음을 완벽히 구분하거나 특정 사용자를 식별하는 기능은 아니다.
- 확인 대기는 자동으로 닫지 않는다. 무음 구간이 끝나면 확인 청취를 다시 시작하고 버튼도 유지한다. 네/아니오 또는 표시된 1/2/3번으로 선택한다. 음성 확인은 설치된 로컬 Whisper 모델을 사용한다.
- 파일/폴더 검색 결과의 상위 3개는 네이티브 resourceId에 연결하여 선택 후 연다. 음성으로 말한 임의 경로를 곧바로 실행하지 않는다. 현재 포트폴리오 전용 모드는 특정 파일 열기만 요청하므로 일반 검색 선택지는 AI 경로에서 해당 검색 요청이 전달될 때 사용된다.
- 수동 닫기는 즉시 화면/마이크를 해제하고 아직 처리하지 않은 요청을 취소한다. 이미 운영체제에 전달한 동작을 되돌린다는 뜻은 아니다. 이전 녹음 결과나 중복 선택이 다음 세션을 실행하지 못하게 세대 번호와 요청 ID를 검사한다.
- 메인 창에서 확인 버튼을 눌러도 음성 확인 녹음을 중단한다. 실행 잠금을 해제한 다음 결과를 전달하여 바로 들어오는 다음 선택이 유실되지 않게 했다. 로그 저장 실패가 오브 결과 전달을 지연시키지 않도록 분리했다.
- 메인 창 접수 응답 자체를 10초 안에 못 받으면 실행 여부가 불확실하다고 알린 뒤 5초 후 닫는다. 이 경우 같은 작업을 자동 재실행하지 않는다. 마이크를 열 수 없는 경우도 재청취가 불가능하므로 안내 후 닫으며, 확인 대기에서는 버튼을 유지한다.

### 인식 설정 비교와 판단

Whisper small-q5_1, 한국어, CPU 4스레드, temperature 0을 유지했다. 설치된 whisper-cli 도움말을 확인하고 빔 탐색 폭 5와 8을 실제 보관 녹음 1개로 비교했다. 이 녹음은 문제의 최근 명령 WAV가 아니며, 정답 명령 인식률을 측정하는 양성 벤치마크도 아니다.

| 설정 | 처리 시간 | 인식 문자 수 | 포트폴리오 열기로 분류 |
|---|---|---|---|
| beam 5 | 6,262ms | 99 | false |
| beam 8 | 7,527ms | 97 | false |

beam 8은 약 20% 느렸으며 정확도 개선 근거가 없어 **기본 5 유지**를 선택했다. 설정 비교용 실행 진입점은 남겼다. 특정 문장을 유도하는 프롬프트나 “포트폴리오예요”를 열기 명령으로 간주하는 유사도 우회는 추가하지 않았다.

확인용 짧은 답변만 최소 유성 구간을 **250ms → 120ms**로 줄였다. 일반 명령은 250ms를 유지한다. 여기서 120ms는 전체 WAV 길이가 아니라 발화로 판정한 구간의 누적 시간이다. “네” 이후의 무음도 WAV에는 포함된다.

설정 후보 비교는 개발자가 같은 음성 자료로 인식 설정/모델의 정확도와 지연을 평가하는 과정이다. 사용자가 비슷한 문장 목록을 직접 작성해야 한다는 뜻이 아니다. 향후 AI 서버는 STT 결과와 문맥에서 의도를 해석하고, 클라이언트는 마이크·UI·확인 응답·안전한 실제 실행을 맡는다. 예/아니오/번호처럼 현재 선택지에 묶인 짧은 응답은 클라이언트에서 결정적으로 처리한다.
