# 캡처·프로필·휴지통·첨부 처리 (2026-10-13)

## 8. 임시 캡처

- 앱 캐시의 `capture-temp/capture-<UUID>.png`와 같은 이름의 JSON 메타데이터 사용
- 메타데이터: taskId, createdAt, expiresAt (UTC Unix 초). 기본 만료 1시간
- 앱 시작 및 60초 주기로 만료 파일 정리. 메타데이터를 쓰기 전에 중단된 파일은 수정 시각 기준 정리
- 결과 확인창에서 사용 중인 이미지는 메모리에 등록해 정리에서 제외. 저장 복사 중에는 같은 잠금을 사용해 삭제와 경합 방지
- 결과 닫기, 새 캡처로 교체, 로그아웃으로 화면 해제 시 사용 종료 후 즉시 삭제. 삭제 실패 파일은 만료 정리에서 재시도
- 캡처 취소/실패는 이미지와 메타데이터 정리. 강제 종료 시 메모리 사용 기록은 사라져 다음 실행의 만료 정리가 처리
- `다른 이름으로 저장`: Windows 사진 폴더의 `ACE Captures`에 PNG 새 파일 생성. 기존 파일 덮어쓰기 금지. 저장 사본에는 정리 메타데이터를 만들지 않음
- 외부 이미지 뷰어의 사용 종료는 감지할 수 없으므로 외부 뷰어 사용 중에는 ACE 결과창을 유지하거나 먼저 사본 저장
- 캡처 업로드 기능은 현재 없음. 향후 업로드를 추가할 때 업로드 완료/취소까지 사용 등록을 유지해야 함

테스트: `화면 캡처해줘` → 모니터 선택 → 다른 이름으로 저장 → 결과 닫기 → 사진/ACE Captures의 사본 유지 확인.
강제 종료 테스트: 캡처 후 ACE를 강제 종료하고 생성 시각부터 1시간 후 재실행 → 임시 PNG/JSON 정리 및 저장 사본 유지 확인.
현재 자동 검사는 임시 디렉터리와 미래 시각, 비어 있는 재시작 사용 기록으로 같은 정리 함수를 검증한 것임. 설치 앱 강제 종료 시험은 수동 검증 대기.

## 9. 프로필

- 설정 상단에서 현재 이메일과 표시 이름 조회
- API 지원 필드인 displayName만 수정. 공백 제외 1~80자 검증
- PATCH /users/me의 성공 응답으로 입력과 인증 사용자 상태 갱신, 사이드바에 즉시 반영
- 저장 중 중복 제출 차단, 실패 시 입력 유지. 재실행은 GET /users/me로 서버 값 조회
- 브라우저 모의 API로 실패→재저장→사이드바 반영→페이지 재접속 검증 통과. 운영 계정 저장/설치 앱 재실행은 수동 검증 대기

## 10. 휴지통

- 기존 Cron 외에 시작 직후 백그라운드 정리. TRASH_CLEANUP_ENABLED=false이면 시작 정리도 비활성
- 한 묶음 최대 100개, 한 실행 최대 100묶음. 묶음 사이에 이벤트 루프에 제어 반환
- 한 실행에서 시도한 ID는 다시 고르지 않음. 실패는 ID와 이벤트만 기록하고 다음 정기 실행에서 재시도
- 실제 PostgreSQL 트랜잭션에서 만료·삭제 조건과 행 잠금을 확인 → 첨부 삭제 예약 → 대화 삭제. 복구와의 경합은 행 잠금으로 직렬화
- 첨부 파일 삭제 예약은 FileDeletionJob에 남겨 DB 삭제 후 프로세스가 중단돼도 재시도 가능
- 파일 삭제는 1분마다 최대 100개, 지수 지연(최대 24시간), 최대 10회 시도. 초과 항목은 DB와 exhausted 로그를 유지하며 관리자 확인 필요
- 모의 DB로 시작 작업·배치 처리·복구된 대상 제외·삭제 실패 재시도 검증. 실제 PostgreSQL에서 동시 복구/중단/재시작 시험은 미실행

## 11. 첨부 저장 결정

- 사용자 확인: 보존할 첨부 파일 없음. 객체 저장소 도입 및 기존 데이터 이전 보류
- 기존 첨부 UI를 다시 추가하지 않음. 로컬 첨부 저장 API는 유지되지만 Render의 로컬 디스크를 영속 저장소로 간주하지 않음
- 임시 음성은 기존 별도 디렉터리·만료 정리 유지, 처리 중인 파일은 정리 제외. 정상/실패 완료 시 기존 remove 경로로 해제·삭제
- 운영 DB/파일 내용을 조회하거나 삭제하지 않음. 객체 저장소의 재배포 후 다운로드 완료 조건은 이번 범위에 해당하지 않음
